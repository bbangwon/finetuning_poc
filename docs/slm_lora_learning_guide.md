## 1. SLM과 파인튜닝의 필요성

### SLM (Small Language Model)이란?
- 파라미터 수 **1B ~ 4B 내외**의 경량 언어 모델 (예: Google Gemma 4 E2B, Llama 3.2 3B, Qwen 2.5 3B).
- 대형 LLM(70B+) 대비 저비용, 온디바이스(PC/모바일) 로컬 구동, 빠른 응답 속도가 특징입니다.

### 사전 학습(Base) 모델의 한계
- 인터넷의 방대한 공개 지식은 잘 알고 있으나, **특정 기업 내부 규정, 비공개 문서, 특정 도메인 포맷**은 전혀 알지 못합니다.
- 사내 질문을 받으면 일반 상식에 기반해 그럴듯하게 거짓말을 하는 **환각(Hallucination)**이 발생합니다.

## 2. 전체 파인튜닝 vs LoRA (PEFT)

| 구분 | 전체 파인튜닝 (Full Fine-Tuning) | LoRA (Low-Rank Adaptation) ★ |
| :--- | :--- | :--- |
| **가중치 변경 방식** | 기존 Base 가중치 전체를 직접 수정 | 기존 Base 가중치는 동결(Freeze)하고 **옆에 작은 보조 층 추가** |
| **학습 파라미터 수** | 모델 전체 100% (수십억 개) | 전체의 **약 0.1% ~ 0.2%** (수백만 개) |
| **메모리(VRAM) 요구량** | 수십 GB 이상 (초고성능 클라우드 GPU 필수) | **4GB ~ 8GB** (Mac M4 Pro 24GB에서 매우 여유) |
| **저장 용량** | 수~수십 GB의 모델 전체 파일 재생성 | **20MB ~ 30MB의 경량 어댑터(`safetensors`)** |
| **파괴적 망각 위험** | 큼 (새 지식 배우다 기존 언어 능력 상실) | 극히 낮음 (기존 모델 가중치가 읽기 전용으로 보존) |
| **서빙 방식** | 태스크마다 별도 모델 서버 구동 | 하나의 Base 모델에 **어댑터만 탈부착(Plug & Play)** |

## 3. LoRA의 핵심 원리: Q, K, V 행렬 보정 메커니즘

트랜스포머 모델의 Self-Attention 블록 내 거대한 가중치 행렬(Query, Key, Value)을 직접 수정하지 않고, **저차원 행렬 분해(Low-Rank Decomposition)**를 적용합니다.

```
                  입력 벡터 x (차원: d)
                     │
           ┌─────────┴─────────┐
           │                   │
           ▼                   ▼
      [ 기존 W ]           [ 행렬 A ]   (d × r, r은 매우 작은 수: 8)
   (d × d, 완전 동결)           │
           │                   ▼
           │               [ 행렬 B ]   (r × d)
           │                   │
           │                   ▼
           │            ΔW = (A × B)   (d × d 차원으로 복원)
           └─────────┬─────────┘
                     ▼ (+) 합산
                 최종 출력 벡터
```

### 수학적 원리
$$\text{Output} = W_{\text{base}}(x) + \Delta W(x) = W_{\text{base}}(x) + (B \times A)(x) \times \frac{\alpha}{r}$$

- **차원 압축 ($r=8$)**: $4096 \times 4096$의 약 1,600만 개 파라미터 대신, $4096 \times 8 + 8 \times 4096 = 65,536$개(약 1/250 수준)만 학습합니다.
- **가중치 보정**: 어댑터는 새로운 지식이 들어왔을 때 기존 출력을 얼마나 비틀어줄지($\Delta W$)만 계산하는 '미세 보정기' 역할을 합니다.

## 4. 왜 빈 가중치에서 1분 만에 학습이 완료되는가?

어댑터를 새로 생성했을 때 아무 가중치도 없는 상태인데도, 어떻게 불과 1분 30초 만에 Base 모델을 망가뜨리지 않고 정확하게 학습되는가?

### ① 초기화의 마법: "투명 인간" (Value = 0) 출발
- **행렬 A**: 평균 0의 가우시안 정규분포(Random Normal)로 초기화.
- **행렬 B**: **모든 원소를 정확히 `0 (Zero)`으로 초기화.**
- **결과**:
  $$\Delta W = B \times A = \mathbf{0} \times A = \mathbf{0}$$
  - 어댑터를 장착한 0초 시점에는 보정값이 정확히 `0`이므로, **기존 Base 모델의 출력과 언어 능력이 100% 온전히 보존**됩니다. (시력 좋은 사람에게 도수 0인 투명 안경을 씌운 것과 같음)

### ② 이미 완성된 지능 위의 "오차(Loss)만 흡수"
- 모델에게 한국어 문법이나 문맥 파악을 처음부터 가르치는 것이 아닙니다. (Base 모델이 이미 언어 능력 100% 보유)
- 모델은 이미 질문 의도를 파악하고 문장을 만들 수 있으며, 단지 **"식대 한도가 15,000원이라는 사내 고유 수치"** 하나만 모를 뿐입니다.
- 역전파(Backpropagation) 시 오차가 동결된 Base 대신 **행렬 B와 A로만 100% 전달**되므로, 0이었던 값들이 몇 번의 스텝(120 Iterations) 만에 최적 가중치로 빠르게 수렴합니다.

### ③ Apple M4 Pro (Unified Memory + Metal) 가속
- CPU와 GPU가 24GB 메모리를 초고속 대역폭으로 단일 공유.
- Metal 최적화 프레임워크인 `mlx`가 초당 190 토큰 이상의 속도로 연산하여 15 에포크 반복 학습을 1분 27초 만에 주파했습니다.

## 5. 사내 규정 Q&A PoC 실습 결과 분석

### 환경 및 모델 사양
- **Base 모델**: `Google Gemma 4 E2B (4-bit MLX)` (~4.07 GB)
- **학습 데이터**: 넥스트웨이브 코퍼레이션 가상 사규 (Train 16건, Valid 4건)
- **평가 데이터**: 미학습 변형 질문 10건

### 정량적 평가 결과
| 구분 | 기본 모델 (어댑터 OFF) | 파인튜닝 모델 (어댑터 ON) | 개선도 |
| :--- | :---: | :---: | :---: |
| **사내 규정 준수 정확도** | **30.0%** (3/10) | **70.0%** (7/10) | **+40.0%p 상승** |
| **어댑터 파일 용량** | - | **26.03 MB** | 초경량 독립 서빙 가능 |
| **학습 소요 시간** | - | **1분 27초** (120 Iters) | M4 Pro 로컬 완결 |

### 1:1 비교 핵심 사례 (Before vs After)

```
[질문: "야근 저녁 밥값 최대 얼마까지 결제할 수 있나요?"]
- 기대 정답: 오후 8시 이후 근무 시 1인당 최대 15,000원

▶ 어댑터 OFF (기본 Base):
  "업무상 야근 식사 비용은 사전 승인된 범위 내에서 처리되며 구체적인 한도는 업무 성격에 따라 달라질 수 있습니다..."
  → ❌ 사규를 알지 못해 모호한 일반론 회피

▶ 어댑터 ON (파인튜닝 후):
  "야근 저녁 밥값은 오후 8시(20:00) 이후 연장 근무할 경우 지원되며, 1인당 한도는 배달팁 포함 최대 15,000원입니다. 결제는 법인카드 사용이 원칙입니다."
  → ✅ 20:00 이후 및 15,000원 한도를 정확히 명시
```

```
[질문: "이번 주 목요일에 집에서 일할 수 있나요?"]
- 기대 정답: 목요일은 전사 코어데이(Core Day)이므로 재택 불가

▶ 어댑터 OFF (기본 Base):
  "재택근무 가능 여부는 부서 운영 방침과 정책에 따라 달라집니다. 소속 부서를 말씀해주시거나 규정집을 확인해주세요..."
  → ❌ 규정을 몰라 사용자에게 되물음

▶ 어댑터 ON (파인튜닝 후):
  "아니요, 화요일과 목요일은 전사 코어데이(Core Day)로 전원 오피스 출근이 필수입니다. 따라서 월/수/금 중에 주 2회를 활용해 주시기 바랍니다."
  → ✅ 화/목 코어데이 금지 규정 완벽 반영
```

## 6. 실무 적용 가이드 및 한계점 (Fine-tuning vs RAG)

실무 엔지니어링 환경에서 SLM을 도입할 때는 파인튜닝과 RAG의 역할을 명확히 분리해야 합니다:

| 항목 | 파인튜닝 (Fine-Tuning / LoRA) | 검색 증강 생성 (RAG) |
| :--- | :--- | :--- |
| **가장 적합한 용도** | **말투, 페르소나, 출력 포맷(JSON 스키마), 사내 보안 수칙 준수** | **자주 바뀌는 사내 매뉴얼, 방대한 지식 검색, 사실 확인** |
| **지식 업데이트 비용** | 데이터셋 재작성 및 모델 재학습 필요 | 벡터 DB 문서 교체만으로 즉시 반영 |
| **출처 인용 (Citation)** | 원문 출처(페이지, 조항) 명시 불가 | 검색된 문서 링크/조항 직접 인용 가능 |
| **추론 시 오버헤드** | 없음 (일반 추론과 속도 동일) | 문서 검색 및 긴 프롬프트 전달로 지연시간(Latency) 발생 |

### 💡 실무 최적 아키텍처: Hybrid 접근법
1. **LoRA 파인튜닝**: 회사의 전문적인 어투, 정해진 응답 형식, 그리고 사내 금기사항(외부 AI 코드 유출 금지 등)을 모델 뼈대에 각인시킵니다.
2. **RAG 결합**: 자주 개정되는 세부 사규나 경비 한도 규정집 문서를 실시간 검색하여 프롬프트의 Context로 함께 주입합니다.
3. **결과**: 환각 없이 최신 사규를 완벽히 인용하면서도, 회사의 표준 양식과 말투로 답변하는 고성능 사내 어시스턴트 완성.
